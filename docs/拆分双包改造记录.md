# 拆分双包改造记录（playbook）

> 本文档记录 `yuppie-mcp-google-sheets` 单包拆分为「纯库包 + MCP 壳包」双包结构的完整过程，含遇到的问题与解决方案。**其他 MCP 仓库需要同样改造时直接套用本文档。**

## 背景与动机

用户通过 PyPI 依赖 `yuppie-mcp-google-sheets`，只想复用其中的 Google Sheets 客户端代码（原 `utils/google/`），但被迫安装 `mcp>=2.0.0,<3.0.0`，与其自己项目的 MCP 版本冲突。

**前置确认（改造任何 MCP 仓库前先做这一步）**：

```bash
# 1. 找出哪些文件 import mcp —— 只有 server.py 一个才适合本方案
grep -rn "from mcp\|import mcp" src/ --include="*.py"

# 2. 确认 utils 层的第三方依赖（应该只有业务库，无 mcp）
grep -rn "^from \|^import " src/<你的包>/utils/ | grep -v "from \."
```

本仓库确认：`src` 中只有 `server.py` import mcp；`tools/` 只依赖 pydantic + utils；`utils/google/` 只依赖 gspread/google-auth/google-api-python-client/requests。

## 方案选型（已踩过的坑）

| 方案 | 结论 |
|------|------|
| mcp 移到 optional-dependencies extras | ❌ 否决。`uvx yuppie-mcp-google-sheets` 默认不装 extras，现有 MCP 用户全部坏掉，破坏性变更 |
| 拆双包，两个都发 PyPI | ❌ 用户不想发新 PyPI 包 |
| **拆双包，库包仅 GitHub 分发（`git+...#subdirectory=`），壳包 vendor 库源码继续发 PyPI** | ✅ 采用。MCP 用户零感知，库用户无 mcp 依赖 |

**关键约束**：PyPI 包的 `dependencies` 不允许 direct reference（git URL），所以壳包不能声明对库包的 git 依赖 → 用 hatch `force-include` 把库源码打进壳包 wheel，实现自包含。

## 目标结构

```
<repo>/                                 # 仓库名不变
├── pyproject.toml                      # workspace 根（不发布，只留 ruff/mypy/pytest 配置）
├── packages/
│   ├── <lib-name>/                     # 新库包 —— 仅 GitHub 分发，永不发 PyPI
│   │   ├── pyproject.toml              # deps: 纯业务依赖（gspread 系），无 mcp 无 pydantic
│   │   ├── README.md                   # 库包自己的 README（git subdirectory 安装说明）
│   │   └── src/<lib_pkg>/              # ← 原 utils/config.py、utils/google/* 拍平上移（config.py + 各 mixin 模块）
│   └── <mcp-name>/                     # 壳包 —— 继续发 PyPI，版本独立演进
│       ├── pyproject.toml              # deps: mcp + 全部业务依赖（vendor 代码运行需要）
│       │                               # force-include: "../<lib-name>/src/<lib_pkg>" = "<lib_pkg>"
│       ├── README.md
│       └── src/<mcp_pkg>/
│           ├── __init__.py             # __version__
│           ├── __main__.py
│           ├── server.py               # 唯一 import mcp 的文件
│           └── tools/                   # ← git mv 原 tools/（MCP 工具层，依赖 pydantic）
├── tests/                              # 留根，testpaths 不变
└── uv.lock                             # uv sync 重新生成
```

用户安装方式：

```bash
# 只要库（无 mcp）
uv add "<lib-name> @ git+https://github.com/<org>/<repo>.git#subdirectory=packages/<lib-name>"
# MCP 用法（不变）
uvx <mcp-name>
```

## 实施步骤

### 1. workspace 根 pyproject.toml

```toml
[tool.uv.workspace]
members = ["packages/*"]

[tool.uv.sources]
<lib-name> = { workspace = true }    # 本地开发时壳包指向库包

[tool.ruff] / [tool.mypy] / [tool.pytest.ini_options]   # 从原根 pyproject 迁移
# mypy 加 mypy_path 指向两个包的 src
```

### 2. 建库包

```bash
mkdir -p packages/<lib-name>/src/<lib_pkg>
git mv src/<mcp_pkg>/utils/config.py packages/<lib-name>/src/<lib_pkg>/config.py
# google/ 子目录拍平上移到包根（包名已含业务域，google/ 是历史层级冗余）
for f in base drive sheets_data sheets_format sheets_quick sheets_table sheets_worksheet visualization; do
  git mv "src/<mcp_pkg>/utils/google/$f.py" "packages/<lib-name>/src/<lib_pkg>/$f.py"
done
# tools 层归壳包（Pydantic 参数模型 + markdown 输出都是为 MCP 服务的）
git mv src/<mcp_pkg>/tools           packages/<mcp-name>/src/<mcp_pkg>/tools
```

- 库包包根 `__init__.py`：`__version__` + 从原 `google/__init__.py` 迁来的 `GoogleSheetsClient` mixin 聚合类定义（`GoogleConfig` 一并 re-export，用户 `from <lib_pkg> import GoogleSheetsClient` 一步到位）
- tools 归壳包后跨包引用库包：`from ..utils.config import` → `from <lib_pkg>.config import`，`from ..utils.google import` → `from <lib_pkg> import`，`from ..utils.google.visualization import` → `from <lib_pkg>.visualization import`（sed 批量）
- **库包因此可去掉 pydantic 依赖**（config 和 client 层都不用 pydantic），依赖最纯

### 3. 迁壳包

```bash
git mv src/<mcp_pkg>/server.py packages/<mcp-name>/src/<mcp_pkg>/server.py
git mv src/<mcp_pkg>/__main__.py packages/<mcp-name>/src/<mcp_pkg>/__main__.py
git mv src/<mcp_pkg>/__init__.py packages/<mcp-name>/src/<mcp_pkg>/__init__.py
rm -rf src
```

- server.py 导入保持 `from .tools import ...`（tools 已归壳包）
- 壳包 pyproject 的 `force-include` 配置（wheel 和 sdist 都要）：

```toml
[tool.hatch.build.targets.wheel]
packages = ["src/<mcp_pkg>"]

[tool.hatch.build.targets.wheel.force-include]
"../<lib-name>/src/<lib_pkg>" = "<lib_pkg>"

[tool.hatch.build.targets.sdist.force-include]
"../<lib-name>/src/<lib_pkg>" = "src/_vendored/<lib_pkg>"
```

### 4. 测试与周边

- tests/ 的 import 改为 `<lib_pkg>.*`（tests 不依赖 mcp，留根即可）
- `uv sync --all-packages --all-extras && uv run pytest -v`
- publish.sh 改为只构建/发布壳包

## 遇到的问题与解决方案 ⚠️

### 问题 1：hatchling readme 不允许项目外路径

```
ValueError: Readme path must be within the project directory: ../../README.md
```

**解决**：子包各复制一份 README.md 到自己目录（`readme = "README.md"`），并在改造完成后为各自写独立内容（壳包 = 主 README + 架构说明；库包 = 安装说明 + 快速开始）。

### 问题 2：uv build 会复制源码到临时目录，force-include 的 `../` 相对路径失效

```
FileNotFoundError: Forced include not found: /Users/.../.cache/uv/sdists-v9/.tmpXXX/<lib-name>/src/<lib_pkg>
```

`uv build` 把包目录复制到 `~/.cache/uv/sdists-v9/.tmpXXX/` 再构建，`../<lib-name>` 在临时目录里不存在。

**解决**：改用 hatch 在原目录构建，相对路径有效：

```bash
cd packages/<mcp-name> && uvx hatch build
```

publish.sh 里同步用这个方式，并在发布前校验 wheel 含 vendor 文件（防止路径失效静默产出残缺包）。

### 问题 3：uv workspace 下 pytest 找不到子包

根 pyproject 无 `[project]` 后，`uv run pytest` 报 `ModuleNotFoundError: No module named '<lib_pkg>'`（脏 .venv + 旧 uv.lock 残留旧单包安装）。

**解决**：`rm -rf .venv uv.lock && uv sync --all-packages --all-extras` 重建。

### 问题 4：git stash -u 会打断 git mv 的索引状态（最大的坑）

验证过程中用了 `git stash -u` 对比 HEAD，导致：
- `git mv` 的 rename 索引被打散，`src/` 被 stash 恢复为 HEAD 原状
- `packages/` 是 untracked 文件，pop 时与残留文件冲突 `already exists, no checkout`
- 根 pyproject 被恢复为旧版

**解决**：`git checkout -- uv.lock`（解除 pop 阻塞文件）→ `rm -rf src`（解除 rename 冲突）→ `git stash pop` → 核对 `find packages -name "*.py"` 文件清单完整性 → drop stash。

**教训**：大规模 `git mv` + 新建文件混合的改动，**验证存量问题时绝不用 `git stash -u`**，改用 `git show HEAD:<path>` 配合 ruff/mypy 的 `--stdin-filename` 直接检查历史版本。

### 问题 5：壳包 README 被截断

用 Write 工具重写壳包 README 时只写了头部（内容是完整文件的子集），产出了 39 行的残缺文件。

**解决**：改用脚本从主 README 复制 + 插入架构说明段落，完成后 `wc -l` 核对行数（147 行 vs 主 README 137 行 + 插入段）。

### 问题 6：目录重排后 editable 安装的实体副本遮蔽 pth

把 `google/` 子目录拍平到包根后，`uv sync` 重装仍然报 `ModuleNotFoundError: No module named '<lib_pkg>.base'`。

原因：uv 的 editable 安装用 `_editable_impl_<pkg>.pth` 指回 src 目录，但 site-packages 里还残留着早期 sync 复制的**实体包目录**（旧布局 `google/`、`tools/`），Python 导入优先命中实体目录，pth 指向的新布局源码被遮蔽。`--reinstall-package` 和删 `.venv` 重建都不清这个残留（dist-info 缓存判断未变）。

**解决**：手动删掉 site-packages 里的实体目录（`.venv/lib/python3.x/site-packages/<lib_pkg>/`），让 pth 生效：

```bash
rm -rf .venv/lib/python3.13/site-packages/<lib_pkg>/
uv run python -c "import <lib_pkg>.base; print(<lib_pkg>.__file__)"  # 应指向 packages/.../src/
```

### 问题 7：本地路径陷阱（shell cwd）

`cd packages/<mcp-name>` 后执行 `uv pip install packages/<lib-name>` 会解析成 `packages/<mcp-name>/packages/<lib-name>`（不存在）。**解决**：安装验证命令一律从仓库根用 `./packages/...` 相对路径或绝对路径。

## 验证清单（改造完成前逐项过）

```bash
# 1. 测试全绿
uv run pytest -v

# 2. 壳包构建 + vendor 校验
cd packages/<mcp-name> && uvx hatch build
unzip -l dist/<mcp_pkg>-*.whl | grep -c <lib_pkg>          # > 0，vendor 成功
unzip -p dist/<mcp_pkg>-*.whl "*METADATA" | grep "^Requires-Dist"  # 无 git URL

# 3. 壳包干净环境 MCP 冒烟
uv venv /tmp/mcp-test && uv pip install --python /tmp/mcp-test <壳包.whl>
/tmp/mcp-test/bin/python -c "from <mcp_pkg>.server import mcp; print(len(mcp._tool_manager._tools), 'tools')"
GOOGLE_CREDENTIALS_B64=dummy timeout 3 /tmp/mcp-test/bin/<mcp-name>  # stdio 阻塞等待即正常

# 4. 库包干净环境（核心目标：无 mcp）
uv venv /tmp/lib-test && uv pip install --python /tmp/lib-test ./packages/<lib-name>
/tmp/lib-test/bin/python -c "from <lib_pkg> import GoogleSheetsClient; print('ok')"
/tmp/lib-test/bin/python -c "import mcp" 2>&1 | grep -q "No module named" && echo "✓ 纯库无 mcp"

# 5. ruff / mypy 与 HEAD 存量对比（确认无新增问题）
uv run ruff check packages/ tests/
uv run mypy packages/*/src
```

本仓库结果：46 测试全绿；wheel vendor 10 个库文件（mixin 平铺后 `yuppie_google_sheets/` 单层）、29 个 MCP 工具可加载；库包干净环境导入 ok 且无 mcp；ruff/mypy 剩余错误与 HEAD 存量完全一致（迁移零新增）。

## 发布流程

只发壳包一个：`scripts/publish.sh`（版本号 sed 目标为壳包 pyproject + 壳包 `__init__.py`；构建用 hatch 原地；发布前自动校验 vendor）。库包版本独立手改，跟随仓库 tag 演进，用户通过 `git+...@v<tag>#subdirectory=` 锁定。
